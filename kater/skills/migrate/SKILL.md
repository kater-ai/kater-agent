# Migrate from Tableau

Move one Tableau dashboard into Kater: a workspace over a shared semantic model, one query for each sheet, and a dashboard in Tableau's order. Then check every tile against the numbers Tableau itself exports, and report each tile as Match, Differs, Changed or Not checked. There is no migration command in Kater: you do every step with your own tools and the `kater` CLI, as this skill and its guide say.

**Lessons.** When `kater ai-tools list` names `lessons` for this skill, read that file before you start and follow it: it is what this organisation learned using this skill. Record a new lesson about using it there, as vfs://guides/lessons.md says.

Read vfs://guides/migrate-tableau.md first, and the part of it for each step as you reach the step. It holds the Tableau calls, what to read in the workbook, the maps from Tableau to Kater and the check's rules.

## When to use

Use this when a person asks to move, migrate, rebuild or copy a Tableau dashboard or workbook to Kater, or to show that Kater's numbers match Tableau's. Run it in the person's own terminal, in their local copy (`kater git clone`): a shared semantic model is made only there. Through the Kater MCP alone, say that and stop. One run moves one dashboard. For a workbook with several, ask which one first.

## The rules

These hold in every run. Never break one to finish faster.

1. **Tableau's numbers come only from Tableau,** in a file written to the disk unchanged: a REST response that a command writes to a file, or a file that Tableau downloaded. Never a number from a picture, a number that you type, or a Tableau MCP answer that you copy into a file.
2. **Kater's numbers come only from `kater run --json`,** written to a file as it answered. Read each `--json` answer whole, as JSON, and never filter it with `grep`: a title such as "Spend (Running Total)" holds any word, and a filtered answer makes a save that worked read as one that failed.
3. **Compare files with a script,** which you write in the capture folder and which reads both files from the disk. Never compare numbers by reading them into your reply.
4. **A Match needs every Tableau column** mapped to a Kater column and every row equal, on the default view and on each filter case. A tile with no Tableau data is Not checked. Not checked never counts as a match.
5. **A difference stays in view.** Fix it, or say why it differs. Never drop a column, change a filter or loosen a rule to make a tile pass. A change made on purpose is Changed, with its reason.
6. **A gap is reported.** When no Kater chart kind or calculation does what a sheet does, build the nearest, mark it Changed, and offer a feature request.
7. **The capture stays on this machine,** in `.kater/migrations/<workbook>/` at the local copy's root, which git never sees. Never put a customer number, a token or a file of the capture in content, a commit, a feature request or a log. Never print the token. A conversation that the person adds to a project on purpose is their choice.

## Procedure

1. **Get the dashboard.** Take the URL or the file from the person's words. With a URL, use the Tableau REST API with the person's personal access token, as the guide's "Get it from Tableau" (vfs://guides/migrate-tableau-capture.md) says. Without a token, ask for one (it takes two minutes in Tableau's account settings), or for the files the guide lists under "Files that Tableau downloaded" (vfs://guides/migrate-tableau-capture.md). Write the capture's files as the guide's "The capture" (vfs://guides/migrate-tableau-capture.md) says, with `capture.md` last.
2. **Read the workbook.** Read its XML as the guide's "Read the workbook" (vfs://guides/migrate-tableau-workbook.md) says: the data sources, tables and joins, the calculations, each measure's number format (its `default-format`), the sheets on the dashboard, the filters, the parameters and the layout. Check the exports' first rows for a prefix or suffix too, such as `4.72x`. Never open an extract, and never copy a connection's credentials.
3. **Write the gap list** in `capture.md`, before you build anything, in four groups: it works in Kater as is, you write it from the guide, the person does it after (such as a dashboard action), or it is not in Kater yet. Before you write it, read the guide's "Filters that Tableau applies later" (vfs://guides/migrate-tableau-workbook.md): each FIXED LOD and each Top N that is not in context goes in the gap list with the shared model's field it needs. For the gaps that are not in Kater yet, first list what your organization already sent with `kater report list --type feature_request`, and name the open report's id beside each gap that one asks for, so you never offer a second request for it. Show the list to the person, and ask in one question whether to go on, whether you may publish the new workspace with `kater git push` once its dashboard is saved (`kater dashboard look` draws only the published copy, and a workspace in the person's own folder stays theirs), and whether you may add the shared model's fields that the list names (a change to a shared model is published only with its own yes). Then end your turn and wait for the answer: never build before it. When the person's request already answers all three, as a request that says yes to each up front does, do not ask: show the gap list and go on.
4. **Find the data.** For each Tableau table, find the connection's dataset in `connections/<connection>/modeling/db_objects/datasets/`. A table in the warehouse but not synced: give the exact `kater sync` line to the person, who may run it, or to an Admin. A table that is not in the warehouse: that data source stops, and the report says what is missing.
5. **Reuse or make the model.** Find a shared semantic model that already reads the tables and has the fields (`kater model show REF`). Add only the fields it lacks. When none does, make one as [model table](vfs://guides/model-table.md) says, with the guide's maps (vfs://guides/migrate-tableau-maps.md). Translate each calculation the dashboard uses, and keep Tableau's formula beside Kater's in `map.md`. A FIXED LOD and a Top N run before Tableau's dimension filters: read the guide's "Filters that Tableau applies later" (vfs://guides/migrate-tableau-workbook.md) before you write them, since a Top N over all rows needs a field in the shared model. Compile the model and what reads it (`kater compile --select 'semantic.MODEL+'`) until there are no errors. That is the whole check of new fields: do not run the model's tests, which take minutes on the warehouse and check fields you did not change.
6. **Write the queries.** Make the workspace and its dashboard with `kater new dashboard NAME --connection CONNECTION --from-model semantic.MODEL`. Write one query for each sheet, as [query authoring](vfs://guides/query-authoring.md) says: picks first, Kater SQL only where no pick makes the field. Add the dashboard's filters with `kater filter`, and each Tableau parameter with `kater parameter add`, such as `--name trend_measure --type string --choice Spend --choice Clicks --default Spend` for a picker (the guide's parameter row). Never write a parameter's entry in the frontmatter by hand. A calculation that picks the measure with a parameter, such as Selected Measure, is the pick `derive.measure_choice`, one choice for each of its branches (the guide's parameter row), never typed SQL. In `map.md`, write each sheet's query, each Tableau column's Kater column and each Tableau filter's Kater filter. Then make each sheet's chart in one command, so that each query is the one its chart draws before any case runs: read its kinds and roles with `kater chart describe <workspace>/<query>`, and a kind's settings with `--kind KIND`, then run `kater new chart NAME --source-query <workspace>/<query> --draw-file DRAW_FILE` (`--source-query` takes `<workspace>/<name>` or the query's id, never its file), with the kind, the roles, the sheet's title, the formats and the sheet's tooltip (the maps' tooltip row). `kater chart draw <workspace>/<chart>` changes a chart that exists.
7. **Check every tile.** Run each query for each filter case with `kater run --json`, 4 cases at a time (the guide's "The check", vfs://guides/migrate-tableau-check.md), write each answer to the capture, and compare with Tableau's file under the guide's "The check". Run each case once: a query you change after the check runs only its own cases again, and a chart's look or a tile's size runs none (the guide's "Run each case once", vfs://guides/migrate-tableau-check.md). Fix each difference that is yours, at most two tries for each tile, then state the reason. Write `report.md` as the guide's "The report" (vfs://guides/migrate-tableau-check.md) says, and name as not verified each column that you typed as Kater SQL and each field that you added to a shared model in this migration: a new model field stays not verified until the data team reviews it (Lee decided this in run c16, 2026-11-02). Take the names from one `kater field show WORKSPACE_FOLDER --reads --json` for the whole workspace, never by hand and never one call for each query: it answers each query, by its `path`, with every field the query reads, also in its filters and its steps (CTEs), and how each was made (`made`). Each field with no `verification` is not verified, except a parameter: a field you add to a shared model has none until a person reviews it. Never run `kater review` yourself. Name each one with its tile in the summary's `Not verified` line and in the `Not verified` column of both the tiles table and the cases table, as the guide's examples show. Never count them as a group.
8. **Build the dashboard.** List the tiles in Tableau's order, and let `kater dashboard save` place and size them, as the guide's "The board" (vfs://guides/migrate-tableau-maps.md) and vfs://guides/dashboard.md say. Choose each chart's kind from the guide's maps (vfs://guides/migrate-tableau-maps.md), and its look from the rules after them, such as the order of a stack, and confirm both with `kater chart describe`. Save the dashboard, then publish the workspace one time with `kater git push`, since the look draws only the published copy. Look at it with `kater dashboard look` beside Tableau's picture, and fix what it reports. Without the person's yes to publish, say that the look waits for it.
9. **Report.** Show the report's summary: how many tiles match, and each tile that does not, with its reason. Name each field as the report does, such as model field, typed or choice, so a choice is never called typed. Name `report.md` for the evidence. Show the dashboard in a new tab with `kater open --new`, which needs no yes. A new tab opens only from a Kater tab that is open: give its link when no tab opened, or when it is refused. Ask before you publish with `kater git push`.
10. **Offer what is next.** For each gap that is not in Kater yet, offer a feature request, as vfs://guides/send-feedback.md says: name the Tableau feature and the sheet, never a number of the capture. For a gap that the gap list names with an open report's id, name its id and offer to add the sheet to it with `kater report comment ID`, never a second request. A send that asks the same as an open report is refused with that report's id: offer the comment then. Then offer to answer the person's own questions on the new workspace.

## Stop and ask

- The dashboard reads a data source that is not in the warehouse, or the person cannot sync the tables.
- A calculation has no translation in the guide, and you are not sure what Tableau computes.
- After two tries, a tile still differs and you cannot say why.
- Tableau refuses the token, or an export fails. Never fill in its numbers in another way.

Never invent a figure, a column or a definition. Report a failure in Tableau's or Kater's own words.
