# Dashboard Reference

A workspace's dashboard is one file, `dashboard.yaml`, at the workspace root beside `workspace.sql`. It declares everything needed to draw the dashboard the same way every time: the template, where every tile sits and how big it is, and the key takeaways. The dashboard is drawn from the file alone; nobody writes code for it. It reads this workspace only; anything that combines workspaces is an app.

Every workspace has one. Creating a workspace scaffolds it, it is scaffolded again the first time it is found missing, and the file cannot be deleted. Only a reader's own filters and open tab are kept outside the file, for that reader. The file keeps no filters, and neither does a chart: each filter's default is in its call ([filters](vfs://guides/filters.md)).

The scaffold is a starting grid in the `contract` template: a band of figures across the top (12 columns, 176px), an 8-column chart beside a 4-column one (both 448px), three 4-column panels (320px), and a 12-column table (576px). Each of the workspace's saved charts, in Explorer order, takes the first slot its shape belongs in; a chart with no slot left follows the grid, and slots no chart took stay empty for a person to fill. A new dashboard has no sections: its tiles draw with no heading until a person puts them in one.

A dashboard made from a template (`--start overview`, `operations`, `realtime` or `transactions`) over a semantic model starts with the template's layout filled from the model's measures, in the model's order: stat cards of the first four measures' totals, a line of the first measure by month of the first date, bars of the first measure for the ten largest values of the first group, and a table of each group with the first six measures. Overview puts them in `tiles` in that order; Operations puts the figures in `kpis`, the line in `primary`, the table in `tiles` and the bars in `rail`; Realtime puts the figures in `kpis`, the line in `hero`, the bars in `aside` and the table in `tiles`; Transactions puts the figures in `figures`, the table as a chart in `ledger` and the line and the bars in `tiles`. Each is a query of the workspace with its chart, saved with the workspace. A measure that cannot be added up across a dimension, such as revenue in many currencies, fills no tile, and a model with no other measure gets one text tile that says so. Change or remove these tiles as for any other; a dashboard with no template starts with the empty grid above.

## Operations

Reach these through the `kater dashboard ACTION`, `kater dashboard text add` and `kater chart draw` commands and `kater insight run`, or the web app and VS Code panel, which call the same operations. A command whose request names only the workspace, the query or the chart takes it as its first argument in place of `--request-file`: a workspace by its folder or its id, the dashboard by its workspace or its own id (`rel1_…`), a query or a chart as `<workspace>/<name>` or its id, such as `kater dashboard open WORKSPACE` or `kater chart read <workspace>/<chart>`. A file is never one.

| Operation | Use |
| --- | --- |
| `dashboard.open` | The file as data (`file`), its `revision`, the resolved dashboard, the check's `problems`, every saved chart name, `saved_charts`: each readable chart's kind and query, and `queries`: every query in the workspace in Explorer order, with or without a chart. A missing file answers with Kater's scaffold, which `scaffold: true` saves for someone who can write the workspace. |
| `dashboard.inputs.read` | The filters and parameters the workspace declares (`declared`), which the dashboard's filter bar draws a control for, with the choices you kept for the dashboard: `kater dashboard inputs read WORKSPACE`. `dashboard.open` does not hold them. |
| `dashboard.save` | Write the whole file. The save gives each tile that has no place and size its own, changes each value the board cannot draw to the one it draws, stores that, and says each change in `problems`. Send the `revision` that `dashboard.open` read it at as `expected_revision`; a stale one is refused. Errors refuse the write. `dry_run: true` returns the file and the problems without writing. |
| `dashboard.tiles.add` | Put one saved chart on the dashboard, or with `query` in place of `chart` a query's own table on the board (`tiles` only). `slot` fills that empty slot in `tiles` at its place and size; a kind that sizes to its content takes its own height. `after` puts it right after that chart's tile, on its tab and in its section, at its size when the chart fits it (a duplicate always does). `region` adds it to another region of the template. Otherwise it goes in `section`, or else the last section with tiles on the tab: at `at` among that section's tiles (0 first), or else into the first empty slot there that suits its kind, or after the section's last tile, placed and sized by the layout planner. Name the tab when the dashboard has tabs, unless you give `after`. `width` asks for `full`, `wide`, `half` or `narrow` in place of the width its kind asks for. |
| `add_to.places`, `add_to.add` | Add to: put a chart, or a query, from another workspace on this dashboard, and on more dashboards, apps and projects in the same add: `kater add-to <workspace>/<chart>` lists every place with its `--to`, and `kater add-to <workspace>/<chart> --to workspace:WORKSPACE` copies the chart and its query into that workspace, reading its root, and puts the chart's tile on its dashboard. A place over another shared model, or one whose root the copy cannot read, answers why it cannot take it. See [the CLI](vfs://guides/kater-cli-commands-masterlist.md). |
| `dashboard.tiles.resize` | Change one tile's size on the board, in words: `kater dashboard tiles resize <workspace>/<chart> --width half --height tall`, with either or both. A query's table goes by its query's `<workspace>/<name>`, and a text or an empty slot by the workspace and `--tile`. `--width` is `full`, `wide`, `half` or `narrow`, and `--height` is `short`, `medium`, `tall` or `tallest`. Every other tile keeps its size. A tile in another region of the template has no size of its own. |
| `dashboard.text.add` | Put one text tile on the board: `kater dashboard text add WORKSPACE --file -` with its words in Markdown on stdin. `--before CHART` or `--after CHART` puts it right before or after that chart, on its tab and in its section. Otherwise it goes at the end of `--section`, or of the last section with tiles on the tab. It takes the whole row unless `--width` says `wide`, `half` or `narrow`, and the board draws it as tall as its words. With `--before` or `--after`, a text less wide than the row shares that chart's row. `--card` draws it on a card. To change or remove a text tile, change its entry in the file and send `dashboard.save`. When you remove one, move each tile that followed it in its row, starting where the one before it ended, left by its width, as the board does when a tile is taken off. |
| `dashboard.layout.suggest` | Shows the place and size that each of a list of charts gets, laid out together from the left edge, with the dashboard.yaml it read as `file` and its `revision`. In a local copy it reads the charts as the copy holds them, as `kater compile` does. Writes nothing. To put charts on the board, use `dashboard.tiles.add`, or list them in `tiles` and send `dashboard.save`. |
| `chart.draw` | Draw a saved chart again from its kind and the columns each role reads, as [make each tile answer one question](vfs://guides/dashboard-tiles.md#make-each-tile-answer-one-question) shows. The chart's spec and SQL are written for you. `tooltip` adds fields to its tooltip, and `presentation.tooltip` renames, hides or adds words: see [the tooltip](vfs://guides/dashboard-tiles.md#the-tooltip). |
| `chart.marker.add` | Draw a line on a chart, at a value or a date: `kater chart marker add QUERY --chart NAME --value FIELD=NUMBER`. See [markers](vfs://guides/pin-and-alert.md#markers). |
| `dashboard.look` | Draw the dashboard as you see it and answer its problems, a line for each tile and its picture: `kater dashboard look WORKSPACE`. See [Look at it](vfs://guides/dashboard-look.md#look-at-it). |
| `insight.run` | Run an insight template over one of the workspace's queries under given inputs. Test a takeaway with it before saving. |

Write the file through `dashboard.save` rather than `write_file`. A hand edit still works: the board draws it as the next save stores it, and the next `dashboard.open` or `compile` reports any problem in it.

## The steps

1. **Write the file:** its template, its tiles and its takeaways, as [the file](vfs://guides/dashboard-file.md) says.
2. **Make each tile answer one question:** [make each tile answer one question](vfs://guides/dashboard-tiles.md).
3. **Look at it** after each change, and fix what the check reports: [look at it](vfs://guides/dashboard-look.md).
