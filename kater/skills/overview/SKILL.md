# Workspace Reference

A workspace is the required boundary for saved analysis. Its root `workspace.sql` contains exactly one `model_type: workspace` declaration over one same-connection shared semantic or Kater dataset, including custom SQL datasets. Its `name` is its folder's name, which is the workspace's one name: queries read it as `workspace.<folder>`, and Kater does not save a root that declares another. Common labels are presentation; typed `source_model` identifies the selected source. The root can tailor its interface with explicit projections, measures, metadata, parameters, and permitted filters. Make those changes, and build its queries, through the typed operations under [Public creation workflow](vfs://guides/public-creation-workflow.md); write SQL by hand only for what no operation expresses. Queries live under `query_contracts/` and read only this root or queries in the same workspace. Charts retain their exact parent query and constrained SQL. The shared compiler reconstructs all three model interfaces in memory; only authored SQL is stored in these model folders. Workspace folders and portable identities are the same locally and in a hosted checkout.

Named-field identity includes the complete workspace path: connection, connection/personal scope, owner, and nested workspace name. Equal names under different owners never share identities or caches. Bare selections and `*` pass fields through and preserve ancestor keys, so a measure stays a measure with the workspace's context added; `EVAL(m)` publishes a value where a pass-through can't stand, and explicit MEASURE/DIMENSION declarations create workspace-owned keys. Editing uses local settings and exact editable occurrences; Sources uses exported capabilities narrowed to the consuming query. See [query contracts](vfs://guides/query-contract.md).

## What a workspace holds

Read `kater model show workspace.NAME` for the workspace's card: its source model, filters, parameters, fields and queries. `kater model show query.WORKSPACE/NAME`, the key `kater model list` gives, shows a query's parts, including its source, fields, sort and limit. REF can also be the model's file from the content root, such as a query's file, which shows that query in its own workspace with no `--scope`. Each card names what the object is made of. The portal draws those same parts as chips, each opening its own card, with View details for every part of a long row.

For a kept query result, `kater model show query.WORKSPACE/NAME --result ID` reads its run's card: the definition it ran, parameter values, filters on or off with their values and resolved dates, fields as the run made them, rows kept and total rows, and the SQL sent to the warehouse with its query ID when one is supplied. A changed saved query is called out beside the definition the run used. Read the run's card when explaining a number from that run; it keeps the run's facts even after the query changes.

- A workspace is the required analysis boundary. Its governed core contains exactly one root `workspace.sql` declaration with `model_type: workspace`, `query_contracts/`, `charts/` and `dashboard.yaml`. A personal app lives beside the person's workspaces, at `connections/<connection>/users/<email>/apps/<app-name>/`, never inside one, and may read query contracts from several workspaces in the same connection. An app in a connection workspace lives in that workspace's `apps/<app-name>/` for now.
- `workspace.sql` declares the workspace's single root interface over one selected shared semantic or Kater dataset. Its frontmatter `name` is the workspace's folder name, which is the workspace model's identity: Kater does not save a root that declares another name, and a rename changes the folder and the `name` together; optional `label`, `description`, `tags`, and multiline `ai_context` provide display metadata and workspace-specific assistant guidance. Workspace declarations cannot set `topic_name` or `topic_category`. Kater writes and compiles this file when it creates a workspace. A workspace created without a source has no SQL in it until `workspace.source` selects one (`kater workspace source use MODEL --scope WORKSPACE`).
- A personal workspace lives at `connections/<connection>/users/<email>/workspaces/<workspace>/`. A connection workspace lives at `connections/<connection>/workspaces/<workspace>/`.
- A command and an answer name a workspace by its folder from the content root, or by its id (`rel1_…`), and a mention by its folder. Make one with `create_workspace`. `list_accessible_workspaces` gives each workspace's folder (`path`), key and id.
- The root's parameters are shared by every query in the workspace. Filters are written in its SQL, each labelled in its own call, with its default (`on=TRUE`) in the call. A filter has one home, the root or one query, and moves up only ([filters](vfs://guides/filters.md#moving-a-filter)). A chart and a dashboard keep no filters: each reader's choices are kept for them, on their page.
- A query contract lives under its workspace's `query_contracts/<domain>/` directory. Query contracts never live in `modeling/`.
- The workspace's query tabs follow `query_order` in `workspace.sql`'s frontmatter: a list of query names, whichever files the queries are in. A query it doesn't name follows the named ones, in file order. Change the order with `query.reorder`, which writes the whole list, as dragging a tab does.
- A workspace can name its comparison date with `comparison_date: FIELD` in `workspace.sql`'s frontmatter. A workspace has one at most, and only the root has the key: a query or a shared model never does. It names a date or timestamp field of the root, best the raw date column, such as `order_date`. Compare reads every figure of the workspace by that field, at each grain the field allows: hour for a timestamp only, then day, week, month, quarter and year, and a field truncated to month allows month, quarter and year. The compile refuses a name that is not a date or timestamp field of the root, and the root's contract publishes the field and its grains as `comparison_date`. Set or change it with the `set_comparison_date` edit in `request.workspace_inputs` of `edit.model`, which names the root, its revision and the field, or `name: null` to take the key out ([public creation workflow](vfs://guides/public-creation-workflow.md)). In the workspace's field list, right-click a date or timestamp field of the root and select Use as comparison date field: a check mark shows on the field in use, selecting it on another field moves the comparison date there, and selecting it on the checked field takes it out. A rename of the field (`kater rename`) renames it in `comparison_date` too, and an edit that takes the field out is refused until the comparison date names another field or is taken out.
- A query can freeze its first rows and columns with `freeze_rows: N` and `freeze_columns: N` in its own frontmatter, each from 0 to 32: its sheet keeps those rows, in the query's order, and those columns in view while the rest scroll. Only a query has the keys. Set them with the `set_freeze` edit in `request.workspace_inputs` of `edit.model`, which names the query, its revision and `rows`, `columns` or both: a number sets its key, 0 takes it out, and a count left out stays as it is. Freeze in the sheet's toolbar sends the same edit. The SQL stays the same, so the next run keeps its rows, and each run's result names the counts as `freeze`.
- A saved chart is a presentation model under the workspace’s `charts/*.sql`, beside `query_contracts/`. Its `markers:` are the lines it draws ([markers](vfs://guides/pin-and-alert.md#markers)). It owns a versioned spec and direct bindings to one query’s published outputs. Business computations, ranks, comparisons, targets and totals remain in the query. Use the public chart operations and exact full identities; never introduce chart aggregation or fabricate card values. An app shows a query through Kater's tags, which draw the same widgets; a chart no kind draws is a `<kater-custom-chart>`, whose page draws the fields it binds inside Kater's card, and any other custom visual draws the rows a `<kater-frame>` hands it. See [apps](vfs://guides/app.md) for composition.
- A workspace has one dashboard. The dashboard is `dashboard.yaml` at the workspace root, and it is Kater's to render: a view of that workspace alone, whose tiles are the workspace's saved charts and which always opens with the workspace's filters and key takeaways. Kater scaffolds the file and refuses to delete it. Change it through the `dashboard.*` operations, writing it with `dashboard.save`, which checks it first (`dry_run` checks without writing); every tile names a saved chart in `charts/`, and every takeaway runs an insight template over one of the workspace's query contracts, so no figure is typed into the file. The reference is [dashboard](vfs://guides/dashboard.md). Apps are stakeholder surfaces, and the one surface that can combine query contracts from several workspaces.
- `modeling/` contains connection-wide datasets, relationships, semantic models, and insight implementations. Shared contains `kater_dataset` (standard or custom SQL) and reusable `semantic` models. Either kind can seed a workspace; use its typed identity and common `label`. No topic concept or metadata exists.
- The cards Explore shows for a shared model are in its Explore file, `explore/<kind>/<name>.explore.yaml` in its model's folder; the file names its model by its typed address in `model:`, such as `model: semantic.ad_reporting`; its file's name is only a label.
- Each connection holds `connection.yaml`, `.kater/`, `ai_tools/`, `modeling/`, `themes/`, `users/` and `workspaces/`. [The content layout](vfs://guides/content-layout.md) has the whole tree.
- A connection is its folder in `vfs://connections/`: it is named once and never renamed or moved.

## Choosing a workspace

- Every analysis, query-contract authoring, compilation, application or dashboard update, and query execution has one exact readable workspace boundary. The one exception is a quick answer in the [Sandbox](vfs://guides/sandbox.md), which reads shared models without a workspace; a statement worth keeping then goes into one. Before treating the selected workspace as final, resolve suitability for the current request. Inspect only the current user's readable personal workspaces and readable connection workspaces; never enumerate or summarize another person's personal workspace for selection. A copy in a brainstorm folder, which every workspace list marks `brainstorm`, is never a candidate: it exists to try a change ([brainstorm folder](vfs://guides/brainstorm.md), Copies).
- Classify candidates as `exact-fit`, `extendable-fit`, `read-pattern-only`, or `not-fit`. Rank required source and field availability first, then semantic meaning, reusable contract availability, writeability for missing objects, and finally continuity with the session. A populated prior workspace is only a tie-breaker, never presumed suitable.
- Reuse the clear best fit. Ask the user only when two candidates would materially change meaning, access, or the durable destination. A readable workspace may supply a useful pattern but is not selected when it cannot answer the question or the person lacks write access for a required change. When no fit exists and the request authorizes creation, create the minimum collision-safe lower-snake-case personal workspace, select one existing same-connection shared semantic or Kater dataset, compile it, and persist the selected per-run workspace in workflow state.
- Read the selected workspace's `workspace.sql` before acting within its boundary. Do not guess a workspace path or infer content from another workspace.

## Where to author

- Author connection-wide datasets, relationships, shared semantic models, and insight implementations in `modeling/` only when the change truly belongs to the connection. Standard Kater datasets enrich one physical `db_dataset`; reusable shared semantics read datasets or other semantics. Shared models cannot own Kater parameters or optional filters. Custom SQL datasets support full connection SQL, including unsynced sources, scripts and, where the warehouse allows them, writes, through their explicit execution/output contract. Workspace roots select exactly one shared semantic or Kater dataset, without a required semantic intermediate; query contracts read that root or queries in the exact same workspace.
- Author the `model_type: workspace` interface and its reusable metadata, parameters, and filters in the selected workspace's root `workspace.sql`. Author query contracts only in that same workspace's `query_contracts/` directory. A query may compose only its root and queries with the same complete workspace identity; charts read their exact parent query. Add and change filters through their typed operations, described under [Public creation workflow](vfs://guides/public-creation-workflow.md), and write a filter call yourself only when none of them can. A query reads a workspace parameter without declaring it again. Preserve activation and inherited ownership.
- Put plans, notes, drafts and workflow runs in your own [brainstorm folder](vfs://guides/brainstorm.md), `brainstorm/` in your own folder, `connection.folder` of `kater_start`, outside every workspace root, each plan as one note named for its question, such as `promote_roas.md`. Keep throwaway SQL there too, in a scratch file, which saves even when a statement doesn't compile ([Sandbox](vfs://guides/sandbox-scratch-files.md)); any other `.sql` file can be saved only where a Kater model lives. To try a change to a workspace, copy it into a topic with `kater brainstorm copy WORKSPACE --topic TOPIC` and change the copy; after the user's yes, `kater workspace apply COPY` writes it back. Model interfaces are compiler-owned and reconstructed in memory; never write one.
- Validate authored sources with `kater compile --select WORKSPACE_PATH`. Execute an exact authored query with `kater run --select <workspace>/<name>`; Run validates its inputs without requiring a prior Compile. Neither operation writes model-contract artifacts. Through the `kater` tool a compile writes nothing to the sources, so it checks any workspace you can read, another person's too. Discover sources with `kater model list` and `kater model fields` before authoring; field browsing lazily inspects metadata and never runs SQL.
- Through the Kater MCP, `kater run` and `kater show` wait for Kater's worker, which builds and runs the query, for up to 35 s. When the answer says the query is still running, run the same command again: it reads the rows that the run keeps, and starts no second run.
