# Physical dataset reference

Read `kater model show db_dataset.NAME` for its card: the warehouse table's database, schema and name, then its columns in table order. Each column's chip opens its column card with its type. Reading the card reads no warehouse rows.

Through the Kater MCP, `kater sync` runs only with `--dry-run`. A person with the right to manage settings runs a real sync with Sync now on the connection's page, or with `kater sync` in their own terminal, so ask them. The `sync.db_dataset` operation (`kater sync --resource-type db_dataset`) writes these files from the warehouse schemas selected in the connection's `connection.yaml`, which you change by hand or with `kater admin connection update`. Sync writes the DDL, column classifications and header, so don't write or edit them yourself. The table's `label` and `description` in the frontmatter are yours to edit, and sync keeps them. Its key is its warehouse table: when the table is renamed in the warehouse, sync moves its file and keeps its `name`. Its `name` is only a label, which you rename with `kater rename db_dataset.NAME NEW_NAME`: it changes every place that names it, its `name:` among them, and its file stays where it is. Never edit the `name` yourself. Each DB dataset in a connection needs its own `name`, which no semantic model or Kater dataset of the connection has; connection.yaml only lists tables by their name in the warehouse. Field labels, descriptions and calculations go in a Kater dataset. `--dry-run` previews, `--check` detects drift, and `--prune` explicitly removes vanished/unselected sources. `kater sync` also updates downstream Kater datasets. See [Sync datasets](vfs://guides/kater-cli-commands-models.md#sync-datasets).

A Source model uses `model_type: db_dataset`. Its SQL is a `CREATE TABLE` declaration in the warehouse's SQL, describing an existing physical object; compiling or running Kater does not execute that DDL or change the warehouse. Sync writes these files under `connections/<connection>/modeling/db_objects/`. For a new table with a label you added, it writes this in a Snowflake connection:

```sql
-- DDL and column classifications are generated by kater sync --resource-type db_dataset. label and description are yours to edit. name follows the warehouse table, and sync renames it when the table changes.
---
name: orders
model_type: db_dataset
label: Warehouse orders
database: RAW
schema: PUBLIC
table: ORDERS
---

CREATE TABLE raw.public.orders (
  -- @categorical
  -- @primary_key
  ID NUMBER(38,0) NOT NULL,
  -- @continuous
  AMOUNT NUMBER(12,2)
);
```

Sync profiles each new column once: `@categorical` or `@continuous` says how its values group, and `@primary_key` marks a column with one row per value and no NULL, the table's key. A column unique in a sample that holds the whole table is unique; in a larger table, the whole table is counted again for that column. A float, a date or time, or a number with a fraction is never a key. Add source reads `@primary_key` to prove that a Kater dataset over the table joins as many to one on that column. `kater sync --resource-type db_dataset --reprofile` profiles every column again, such as columns synced before sync recorded uniqueness. `-- @foreign_key` marks a column whose value is another table's key and repeats here. Only a dataset writes `@primary_key` or `@foreign_key`, at most one on a field and with no argument, and every field that reads the column by plain reference, through a cast or parentheses too, has the key with the dataset that declares it.

In a DuckDB connection, the same table's columns are `id INTEGER NOT NULL` and `amount DECIMAL(12,2)`: sync writes each type as the warehouse's DESCRIBE names it, and each name as the warehouse folds it.

The DDL establishes the physical database, schema, table, column order, types, and nullability. Preserve quoted identifiers exactly, including case and spaces. Names follow the warehouse's rule. Snowflake folds an unquoted name to upper case and keeps a quoted one as written, so `"Sales DB"."Public"."Order Facts"` is a different address from an unquoted triple. DuckDB ignores case, quoted or not. The frontmatter `database`, `schema` and `table` are required: they name the table, and they must agree with the DDL. A DB dataset without them gets `database_identity_missing`. Columns are nullable unless marked `NOT NULL`. The compiler reads each type as the warehouse spells it, with its precision and scale.

The supported declaration has a nonempty explicit column list and optional `OR REPLACE` and, in Snowflake, `TRANSIENT` modifiers. Empty bodies, unqualified targets, duplicate columns, malformed types, `CREATE TABLE AS SELECT`, defaults, and unsupported constraints receive diagnostics. A compiled physical model supplies a typed read projection for inspection; it remains non-runnable through the public Run operation.

Field declarations, labels, descriptions, AI context, and required filters belong in a [standard Kater dataset](vfs://guides/dataset__kater.md) over the table: `sync.kater_dataset` (`kater sync --resource-type kater_dataset`) writes its base declarations from this DDL, and its fields change through the operations under [Public creation workflow](vfs://guides/public-creation-workflow.md). Physical SQL addresses remain `DATABASE.SCHEMA.TABLE`; `db_dataset.orders` is not a second physical address. The central [model policy](vfs://guides/model-layer-rules.md) governs permitted consumers.

## Declared and suggested keys

The sync reads the warehouse's declared primary, unique and foreign keys. It verifies a declared or sampled primary key against the whole table before writing `@primary_key`. A repeated or empty value disproves the claim, so no primary key is written and each sync warns why. A declared foreign key is written without a uniqueness count. Multi-column constraints do not become column directives.

A column name ending in the word ID, KEY, HASH, UUID or GUID only suggests a foreign key; it never writes one by itself. Accept a suggestion with `kater sync --resource-type db_dataset --foreign-key orders.customer_id`, or remove it with `--no-foreign-key orders.customer_id`. Later syncs keep the person's choice. `--no-profile` accepts metadata and choices without sampling rows. The baseline records every checked column as primary, foreign or neither and records whether the evidence came from the warehouse, data or a person. An unchanged sync checks no column again; new or retyped columns are checked, and `--reprofile` explicitly checks all. Every sync statement uses the query tag `kater_dataset_sync`, so its cost can be read from warehouse history.
