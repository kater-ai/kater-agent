# Physical dataset reference

Read `kater model show db_dataset.NAME` for its card: the warehouse table's database, schema and name, then its columns in table order. Each column's chip opens its column card with its type. Reading the card reads no warehouse rows.

Through the Kater MCP, `kater sync` runs only with `--dry-run`. A person with the right to manage settings runs a real sync with Sync now on the connection's page, or with `kater sync` in their own terminal, so ask them. The `sync.db_dataset` operation (`kater sync --resource-type db_dataset`) writes these files from the warehouse schemas selected in the connection's `connection.yaml`, which you change by hand or with `kater admin connection update`. Sync writes the DDL, column classifications and header, so do not write or edit them yourself. The table's `label` and `description` in the frontmatter are yours to edit, and sync keeps them. Its key is its warehouse table: when the table is renamed in the warehouse, sync moves its file and keeps its `name`. Its `name` is only a label, which you rename with `kater rename db_dataset.NAME NEW_NAME`: it changes every place that names it, its `name:` among them, and its file stays where it is. Never edit the `name` yourself. Each DB dataset in a connection needs its own `name`, which no semantic model or Kater dataset of the connection has; connection.yaml only lists tables by their name in the warehouse. Field labels, descriptions and calculations go in a Kater dataset. `--dry-run` previews, `--check` detects drift, and `--prune` explicitly removes vanished/unselected sources. `kater sync` also updates downstream Kater datasets. See [Sync datasets](vfs://guides/kater-cli-commands-models.md#sync-datasets).

A Source model uses `model_type: db_dataset`. Its SQL is a `CREATE TABLE` declaration in the warehouse's SQL, describing an existing physical object; compiling or running it never executes that DDL or changes the warehouse. Sync writes these files under `connections/<connection>/modeling/db_objects/`. For a new table with a label you added, it writes this in a Snowflake connection:

```sql
-- DDL and column classifications are generated by kater sync --resource-type db_dataset. label and description are yours to edit. name follows the warehouse table, and sync renames it when the table changes.
---
name: orders
model_type: db_dataset
label: Warehouse orders
database: RAW
schema: PUBLIC
table: ORDERS
---

CREATE TABLE raw.public.orders (
  -- @categorical
  -- @primary_key
  ID NUMBER(38,0) NOT NULL,
  -- @continuous
  AMOUNT NUMBER(12,2)
);
```

Sync profiles each new column once: `@categorical` or `@continuous` says how its values group, `@timeframe__month` says a date is already kept by month (see [A date's own grain](#a-dates-own-grain)), and `@primary_key` marks a column with one row per value and no NULL, the table's key. A column unique in a sample that holds the whole table is unique; in a larger table, the whole table is counted again for that column. A float, a date or time, or a number with a fraction is never a key. Add source reads `@primary_key` to prove that a Kater dataset over the table joins as many to one on that column. `kater sync --resource-type db_dataset --reprofile` profiles every column again, such as columns synced before sync recorded uniqueness. `-- @foreign_key` marks a column whose value is another table's key and repeats here. Only a dataset writes `@primary_key` or `@foreign_key`, at most one on a field and with no argument, and every field that reads the column by plain reference, through a cast or parentheses too, has the key with the dataset that declares it.

In a DuckDB connection, the same table's columns are `id INTEGER NOT NULL` and `amount DECIMAL(12,2)`: sync writes each type as the warehouse's DESCRIBE names it, and each name as the warehouse folds it.

The DDL establishes the physical database, schema, table, column order, types, and nullability. Preserve quoted identifiers exactly, including case and spaces. The DDL's names follow the warehouse's rule. Snowflake folds an unquoted name to upper case and keeps a quoted one as written, so `"Sales DB"."Public"."Order Facts"` is a different address from an unquoted triple. DuckDB ignores case, quoted or not. The frontmatter `database`, `schema` and `table` are required: they name the table, and they must agree with the DDL. A DB dataset without them gets `database_identity_missing`. Columns are nullable unless marked `NOT NULL`. The compiler reads each type as the warehouse spells it, with its precision and scale.

The supported declaration has a nonempty explicit column list and optional `OR REPLACE` and, in Snowflake, `TRANSIENT` modifiers. Empty bodies, unqualified targets, duplicate columns, malformed types, `CREATE TABLE AS SELECT`, defaults, and unsupported constraints receive diagnostics. A compiled physical model supplies a typed read projection for inspection; it remains non-runnable through the public Run operation.

Field declarations, labels, descriptions, AI context, and required filters belong in a [standard Kater dataset](vfs://guides/dataset__kater.md) over the table: `sync.kater_dataset` (`kater sync --resource-type kater_dataset`) writes its base declarations from this DDL, and its fields change through the operations under [Public creation workflow](vfs://guides/public-creation-workflow.md). Physical SQL addresses remain `DATABASE.SCHEMA.TABLE`; `db_dataset.orders` is not a second physical address. The central [model policy](vfs://guides/model-layer-rules.md) governs permitted consumers.

## Declared and suggested keys

The sync reads the warehouse's declared primary, unique and foreign keys. It verifies a declared or sampled primary key against the whole table before writing `@primary_key`. A repeated or empty value disproves the claim, so no primary key is written and each sync warns why. A declared foreign key is written without a uniqueness count. A `@primary_key` line that the file holds and no sync has checked stays: each sync that saves counts it over the whole table, `--no-profile` and a scheduled sync too, and takes it out only when the count or the column's type disproves it, which the sync reports as `key_changed`. A table with no rows disproves nothing. `--foreign-key` on such a column counts it first, in a plan too: a unique column stays the primary key, and any other becomes the foreign key. When the count cannot say, the line stays and the mark waits for the next sync that saves. Multi-column constraints do not become column directives.

A column name ending in the word ID, KEY, HASH, UUID or GUID only suggests a foreign key; it never writes one by itself. Accept a suggestion with `kater sync --resource-type db_dataset --foreign-key orders.customer_id`, or remove it with `--no-foreign-key orders.customer_id`. Later syncs keep the person's choice. `--no-profile` accepts metadata and choices without sampling rows; a column with an unchecked `@primary_key` line is still counted. The baseline records every checked column as primary, foreign or neither and records whether the evidence came from the warehouse, data or a person. An unchanged sync checks no column again; new or retyped columns are checked, and `--reprofile` explicitly checks all. Every sync statement uses the query tag `kater_dataset_sync`, so its cost can be read from warehouse history.

## A date's own grain

A date or timestamp column can be kept coarser than its type, such as a DATE that holds only the first day of each month. `-- @timeframe__month` above the column says so. A field that reads it offers Month, Quarter and Year and nothing finer, and says Month beside its name, as a field made with `KATER__MONTH` does. The word is the grain: `@timeframe__hour`, `@timeframe__day`, `@timeframe__week`, `@timeframe__month`, `@timeframe__quarter` or `@timeframe__year`. A timestamp that is always at midnight is kept by day. A field that reads the column by plain reference, through a cast, parentheses, `MIN`, `MAX` or `ANY_VALUE` too, has the same timeframe.

A directive that is one bare word says what was found about the data: `@categorical`, `@continuous`, `@primary_key`, `@foreign_key` and `@timeframe__month`. A directive with a value is what an author sets: `@format id`, `@sort_by month_number` and `@tags "growth"`. So the line says what the column already is, and `KATER__MONTH` changes what a field is.

Sync writes the line, so nobody has to write anything to say what the table already shows. For each date or timestamp column it reads the whole table in one aggregate query and finds the coarsest grain that every value that is not NULL is at: the first moment of an hour, day, week, month, quarter or year, or, for a month, quarter or year, its last day. A week is found only when every value is the warehouse's first day of the week. A column with fewer than three different values proves nothing, and sync writes no line. A preview (`--dry-run`) reads no values and so writes no line. A wrong line hides finer rows from the field picker and changes no number, since a month truncated again is the same month.

A person only corrects what sync found. Change the word, or take the line out: a line you took out stays out, and sync keeps that in `.kater/dataset-sync/`. Write one by hand where sync cannot see the fact. Sync keeps a line you wrote and checks it with a looser test, that no two different values fall in one period; when two do, each sync warns with them and keeps the line. A later sync checks each line it holds, and a scheduled sync does too, in one aggregate query for the table. When a value breaks a line that sync wrote, sync takes the line out and warns with the value. A scheduled sync finds the grain of no new column: a new column waits for a person's sync, as its classification does.

Only a DB dataset holds the line, because it is a fact about a table. A Kater dataset, custom SQL included, states its grain in SQL with `KATER__MONTH`, and a line there is refused. The line is refused on a column that is no date or timestamp, on a unit the column's type lacks (a DATE has no hour), and on any other model, each refusal naming the dataset.

An agent that is asked for a grain finer than a field's own, such as revenue by week from a field kept by month, is refused with the field's words: "Revenue Month is kept by month. Select Month, Quarter or Year." (`query.new`, and the edit operations `timeframes.set` and `timeframes.add`). `kater field show` prints the same list in its `Timeframes` line. Tell the person what the refusal says, that the data is kept by month and month is the finest view, and show the figures at the finest grain the field offers, in the same answer and with no question: run a query in one of the person's own workspaces (`kater query new`, after create_workspace on the same model when none of theirs reads it), since a query in a shared workspace is refused to the agent (`write_limited`) and waiting for a yes shows the person nothing. Never rebuild the figure at the finer grain from another workspace or model, and never offer or recommend that: it counts something else. Never write `KATER__WEEK` or `DATE_TRUNC('week', ...)` over the field to get the week: it names each bar for a week when it holds a whole month.
